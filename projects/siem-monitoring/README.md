# SIEM monitoring lab

Учебная реконструкция задач SOC из резюме: сбор Windows/Linux/Sysmon, корреляция неудачных входов и проверка подозрительных запусков PowerShell. Проект содержит работающий **офлайн-анализатор** и отдельные заготовки конфигурации Wazuh. Это собственная учебная реализация, а не исходники работодателя, выгрузка производственной системы или подтверждение внедрения.

Python 3.11+; только стандартная библиотека, без установки зависимостей и Docker. Все команды ниже выполняются **из корня репозитория**.

## Быстрый запуск

```bash
python projects/siem-monitoring/run.py --input projects/siem-monitoring/data/events.jsonl
python projects/siem-monitoring/run.py --input projects/siem-monitoring/data/events.jsonl --output projects/siem-monitoring/examples/report.json
python -m unittest discover -s projects/siem-monitoring/tests -v
```

Первый запуск выводит JSON в терминал, второй сохраняет тот же детерминированный результат. В примере **21 событие и 5 оповещений**: серии неудачных входов на Windows и Linux, два запуска PowerShell с индикаторами для проверки и серия от условного согласованного сканера. Адреса — документальные диапазоны, домен — `example.invalid`, имена и команды синтетические. Команды из событий хранятся как текст: анализатор их не исполняет и не декодирует.

Проверка исключения для известного сканера:

```bash
python projects/siem-monitoring/run.py --input projects/siem-monitoring/data/events.jsonl --allow-source-ip 198.51.100.10
```

Результат: 4 оповещения, `allowlisted_failure_events: 5`. Исключение применяется только к ошибкам аутентификации, не к запуску PowerShell. `--allow-source-ip` можно повторить; поддерживаются точные IPv4/IPv6, не CIDR. Источник должен быть проверен вручную: исключение доверенного адреса может скрыть атаку с этого адреса. Исключений по имени учетной записи нет.

Порог можно изменить; оба параметра проверяются:

```bash
python projects/siem-monitoring/run.py --input projects/siem-monitoring/data/events.jsonl --failure-threshold 6 --window-seconds 180
```

`--input -` читает stdin, `--output -` пишет stdout. Ошибка входа возвращает код `2`, сообщение с номером строки и не перезаписывает существующий отчет. Входной файл нельзя выбрать как выходной: проверяются также символьные и жесткие ссылки на тот же файл. Код `0` означает успешный анализ, даже если обнаружены оповещения. Каталог для `--output` должен существовать.

## Схема событий и корреляция

Вход — UTF-8 JSONL, один JSON-объект на строку; пустые строки разрешены. Обязательны непустые строковые `event_key` (уникален в файле), `timestamp` (ISO 8601 с часовым поясом), `host`, `account`, `source` и `event_type`. `source`: `windows_security`, `linux_auth`, `sysmon`. `event_type`: `authentication_failed`, `authentication_success`, `process_start`. Дополнительно: `source_ip` — строка с IP; для `process_start` обязательны `process_name` и `command_line`. Неизвестные поля игнорируются. Это **нормализованная учебная схема**, не нативный JSON Wazuh и не формат Windows Event XML; адаптеры настоящих логов в проект не входят.

| Сценарий | Логика | Что проверять аналитику |
| --- | --- | --- |
| Неудачные входы | По умолчанию 5 событий за 300 секунд включительно, отдельная группа `(host, account)` | Смену пароля, сохраненные учетные данные служб, источник и соседние успешные входы |
| PowerShell с `-EncodedCommand` / `-enc` | Только процессы `powershell(.exe)` / `pwsh(.exe)`, регистр не важен | Кто запустил команду, назначение кодировки и согласованную автоматизацию |
| PowerShell с загрузкой и выполнением выражения | В командной строке вместе встречаются `IEX` / `Invoke-Expression` и индикатор загрузки | Источник скрипта, родительский процесс, подпись и ожидаемое поведение |

Перед корреляцией все события сортируются по UTC-времени, затем по `event_key`; порядок строк не влияет на результат. Имена хостов и учетных записей сравниваются точно: канонизацию доменов и регистра выполняет будущий адаптер. Источники внутри одной группы суммируются: событие Windows и Linux с одинаковыми `host/account` попадет в одну группу. IP входят в доказательства, но не разделяют счетчик — это позволяет увидеть распределенные попытки для одной учетной записи. Успешный вход не сбрасывает историю ошибок.

После достижения порога плотная серия не создает оповещение на каждое следующее событие. Перед каждой новой ошибкой удаляются события старше окна. Если оставшийся счетчик упал ниже порога, группа снова может создать оповещение при достижении порога; после паузы дольше окна начнется новая серия. Поэтому длительная активность на границе окна может дать повторные оповещения. Каждое содержит время, хост, учетную запись, IP, ссылки на синтетические `event_key`, объяснение и `requires_review`. Это сигнал для проверки, а не вердикт о компрометации. Счетчик `failed_authentication_events` включает исключенные ошибки, отдельный счетчик показывает число исключений.

## Конфигурация Wazuh

Файлы в `wazuh/` — отдельная конфигурация с базовой совместимостью по структуре правил Wazuh **4.12**. Python-анализатор их не загружает. Нет утверждения, что XML и Python имеют побитно одинаковые результаты: Wazuh использует свои декодеры, поля, очередность правил и счетчики, а офлайн-анализатор пересортировывает весь файл по времени.

| Файл | Назначение |
| --- | --- |
| `wazuh/windows-agent.fragment.xml` | Сбор Security 4624/4625 и Sysmon Process Create 1 агентом Windows |
| `wazuh/linux-agent.fragment.xml` | Сбор `/var/log/auth.log` на Debian/Ubuntu с файловым auth-журналом |
| `wazuh/local_rules.xml` | Правила менеджера 110001–110022 для Windows failures, Linux SSH failures и PowerShell |

Для Windows отдельно нужны настроенный аудит входов и установленный Sysmon, который пишет Process Create. Для Linux путь зависит от дистрибутива: проверьте `/var/log/secure` либо настройте journald, если файла нет. Блоки `localfile` следует объединить с существующей конфигурацией агента, предварительно исключив дублирование уже настроенного сбора. Адрес менеджера, регистрация агентов и TLS здесь не задаются.

Перед использованием в своей изолированной лаборатории нужно проверить свободные ID и добавить правила в `/var/ossec/etc/rules/local_rules.xml`, сохранив существующие правила. У Windows-правил указаны конкретные встроенные родители: `60122` для ошибки входа и `61603` для Sysmon Process Create. Это сохраняет категорию `ossec` и помещает расширения в дерево, уже выбранное стандартными Windows-правилами. Структура родителей сверена с исходными правилами Wazuh 4.12: [Windows Security](https://github.com/wazuh/wazuh/blob/v4.12.0/ruleset/rules/0580-win-security_rules.xml), [Sysmon](https://github.com/wazuh/wazuh/blob/v4.12.0/ruleset/rules/0595-win-sysmon_rules.xml). На другой версии сначала нужно проверить эти ID и дерево правил.

Корреляция Windows использует поля `win.eventdata.targetUserName` и `win.system.computer`; Linux SSH — декодированного пользователя и стандартную изоляцию счетчиков Wazuh по агенту. `global_frequency` не включен. PowerShell зависит от `win.eventdata.image`, `win.eventdata.commandLine` и Sysmon provider. Наличие и написание этих полей проверяются на фактическом выводе декодера. Фрагменты не содержат allowlist: параметр Python на правила Wazuh не влияет.

В среде с установленным менеджером администратор лаборатории проверяет конфигурацию и реальные декодированные тестовые записи:

```bash
/var/ossec/bin/wazuh-analysisd -t
/var/ossec/bin/wazuh-logtest
```

Эти две команды выполняются на машине менеджера, **не из этого репозитория**. В `wazuh-logtest` нужно проверить одиночные события, серию на точной границе окна, разные хосты/пользователей и согласованную автоматизацию; успешная XML-проверка не доказывает срабатывание корреляции. **Wazuh здесь не устанавливался и внешняя проверка Wazuh не запускалась**. До интеграционного теста правила остаются заготовкой для лаборатории.

## Проверка и ограничения

19 unittest-проверок покрывают сортировку событий, изоляцию групп, границу и истечение окна, повторные серии, успешный вход, ограниченность исключений, безобидные команды, индикаторы PowerShell, часовые пояса, ошибки JSON/схемы, повторные ключи, CLI, защиту входа от перезаписи через тот же путь/ссылки и воспроизводимость примера. XML дополнительно можно проверить стандартным парсером, но это не заменяет Wazuh:

```bash
python -c "from pathlib import Path; import xml.etree.ElementTree as E; [E.parse(p) for p in Path('projects/siem-monitoring/wazuh').glob('*.xml')]; print('XML syntax OK')"
```

Вход полностью хранится в памяти; для непрерывного SOC-потока нужны состояние, ограничение памяти и обработка поздних событий. Здесь нет передачи в Wazuh, поиска по индексам, реагирования и исполнения команд. Текстовые регулярные выражения могут пропустить другие сокращения, обфускацию и альтернативные способы запуска PowerShell; слова в комментарии или строковом литерале могут дать ложное срабатывание. Кодировка сама по себе не доказывает вредоносность. Для практической настройки нужны размеченные разрешенные примеры, контекст процесса, оценка пропусков и ручной разбор false positive. Производственные логи и персональные данные в учебный набор не включены.
